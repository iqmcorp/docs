## About HCP proposals

An HCP proposal is a media plan that targets healthcare professionals by their National Provider Identifier (NPI) type, specialty, location, and data partner. Unlike Political proposals, HCP proposals have no separate plan and strategy stages: a proposal is created directly with its targeting and proposed campaigns.

**Generate campaigns → Save proposal → Edit (optional) → Publish IO and campaigns**

Two rules make HCP proposals harder than they look:
  1. **Targeting consistency.** The split strategy must agree with the proposal's plan-level targeting, or the request is rejected. See [Step 1](#step-1-plan-the-audience-and-targeting).
  1. **Status echo.** Every edit and publish request must include the proposal's *current* <var>statusId</var>. See [Step 5](#step-5-edit-the-proposal).

An HCP proposal has one of the following statuses. See [Proposal status list](/guidelines/planner-api#proposal-status-list) and pass <var>plannerTypeId</var> <var>2</var> for HCP statuses.

| Status ID | Status |
| --- | --- |
| <var>2</var> | Draft |
| <var>6</var> | Ready |
| <var>5</var> | Processing: IO and campaigns are being created |
| <var>7</var> | IO Created: publishing finished and the IO exists |
| <var>4</var> | Failed: publishing failed and can be retried |
| <var>3</var> | Expired: the proposal's end date has passed |

### Step 1: Plan the audience and targeting

Before calling any endpoint, decide who the proposal targets and how its campaigns are split. These choices make up the body of every request in the following steps. See [HCP Planner resource properties](/healthcare-vertical/planner#hcp-planner-resource-properties) for all fields.

#### NPI types

`npiTypeIds` sets which professionals to reach. Get values from the [NPI type list](/healthcare-vertical/planner#npi-type-list).

<EnumWidget values={npiTypes} />

#### Audience blocks

`audienceBlocks` defines the audience. Each block uses one audience selection method, set by <var>audienceSelectionMethodId</var>, and the fields a block needs depend on its method. Use at most one block per method. See [Get audience selection methods list](/healthcare-vertical/planner#get-audience-selection-methods-list).

| Method | ID | Required block fields | Audience type |
| --- | --- | --- | --- |
| Filter based | <var>1</var> | <var>speciality</var>, <var>locations</var>, <var>dataPartners</var> | Matched (<var>1</var>) |
| Upload NPI list | <var>2</var> | <var>speciality</var>, <var>locations</var>, <var>dataPartners</var>, and <var>storagePathId</var> from an uploaded NPI file | Matched (<var>1</var>) |
| Existing audience | <var>3</var> | <var>includeAudienceIds</var> and/or <var>excludeAudienceIds</var>, up to 14 in total. Don't send specialty, location, or data partner fields. | Taken from the selected audiences |
| Account based | <var>4</var> | <var>speciality</var>, <var>locations</var>, <var>account</var>, <var>accountType</var>, <var>healthSystem</var>, <var>title</var>, <var>dataPartners</var>. Requires NPI type <var>3</var>. | ABM (<var>9</var>) |

For filter-based blocks:
  * `locations.countryId` must be <var>30100001</var> (United States)
  * `dataPartners` is a list of partners with at least one marked <var>selected: true</var>. See [Get data partners list](/healthcare-vertical/planner#get-data-partners-list); the active partners are <var>7</var>, <var>8</var>, <var>11</var>, and <var>12</var>.
  * `speciality` uses the "select all" pattern described below. See [Get specialties list](/healthcare-vertical/planner#get-specialties-list).

The audience type of each block is set by IQM from its method, as in the table above. Don't send <var>selectedAudienceTypeIds</var>; it is ignored.

#### Plan-level targeting

`planLevelTargeting` sets the creative types and devices for the whole proposal. Objects such as <var>creativeTypes</var>, <var>devices</var>, and <var>speciality</var> use a "select all" flag with an ID list:

  * Select all: set the flag (for example <var>allCreativeTypesSelected</var>) to <var>true</var> and send an empty ID list
  * Select specific values: set the flag to <var>false</var> and list the IDs

Any other combination is rejected.

#### Split strategy and the targeting consistency rule

`splitStrategy` decides how the proposal is divided into campaigns. Each entry names a [split dimension](/healthcare-vertical/planner#get-split-strategy-list) and the values to split by. Each listed value becomes its own campaign slice, and campaigns are created for every combination of slices. A split strategy must include the creative type dimension, and the NPI type dimension unless the only audience block is an existing audience.

The values in each split dimension must agree with the proposal's targeting. This is the most common cause of rejected HCP requests. See [Targeting consistency rule](/healthcare-vertical/planner#targeting-consistency-rule).

| Split dimension | `splitDimensionTypeId` | `selectedValueIds` must agree with | Rule | Campaign field |
| --- | --- | --- | --- | --- |
| Creative type | <var>1</var> | `planLevelTargeting.creativeTypes.creativeTypeIds` | Exact match | `targeting.creativeTypeId` |
| NPI type | <var>2</var> | `npiTypeIds` | Subset | `targeting.npiTypeId` |
| Data partner | <var>3</var> | `dataPartners[].id` across all audience blocks | Subset | `targeting.dataPartnerIds` |
| Device type | <var>4</var> | `planLevelTargeting.devices.deviceTypeIds` | Subset | `targeting.deviceTypeIds` |
| Audience type | <var>5</var> | Audience types of all audience blocks | Subset | `targeting.audienceTypeIds` |

When "select all" is used for creative types or devices, compare against the full list: creative types <var>11</var>, <var>13</var>, <var>14</var>, <var>15</var>, and <var>17</var>; devices <var>20300001</var> to <var>20300004</var>.

:::caution

Mismatches are reported with a general message, such as <var>Selected creative type IDs and split IDs do not match.</var> Check the dimension named in the message against the table above.

:::

Each proposed campaign's targeting uses singular fields for creative and NPI type (<var>creativeTypeId</var>, <var>npiTypeId</var>), unlike the plural fields at the plan level. Campaign targeting isn't checked against the split strategy, so let IQM build the campaigns in [Step 2](#step-2-generate-campaigns) rather than writing them yourself.

### Step 3: Create a ready proposal

<CopyUrl method="POST" url="https://api.iqm.com/api/v3/plan/hcp/proposal/add" operationId="createProposal_1" />

<div class="endpoint-container">
  <div class="child1">

Save the proposal in <var>Ready</var> (<var>6</var>) status. Send the full response <var>data</var> from Step 2 as the request body. Save the <var>id</var> from the response; it's the <var>planId</var> used in the following steps.

### Step 6: Publish the IO and campaigns

<CopyUrl method="POST" url="https://api.iqm.com/api/v3/plan/hcp/campaigns/publish" operationId="generateIOCampaigns_2" />

<div class="endpoint-container">
  <div class="child1">

Publish the proposal to create an IO and campaigns. Send the full proposal with its <var>id</var> and current <var>statusId</var>, as in Step 5. Publishing saves the request body first using the same checks as an edit, so the [status echo rule](#step-5-edit-the-proposal) applies here too.

The request returns immediately and the proposal moves to <var>Processing</var> (<var>5</var>) while the audiences, IO, and campaigns are created in the background. When publishing finishes, the proposal moves to <var>IO Created</var> (<var>7</var>) and its <var>ioId</var> is set. If publishing fails, the proposal moves to <var>Failed</var> (<var>4</var>) and you can publish it again. The response doesn't include the IO ID: use [Step 4](#step-4-get-proposal-details) to check the result.

| Request schema |  |
| ---- | --- |
| `id` <br /><span class="type-text">integer</span> <span class="required-text">required</span> | Proposal ID from Step 3 |
| `statusId` <br /><span class="type-text">integer</span> <span class="required-text">required</span> | The proposal's current status ID from Step 4 |

All other fields are the same as [Step 5](#step-5-edit-the-proposal).

:::danger

Publishing is a one-way step. A published proposal can't be returned to <var>Ready</var>, and calls that require a <var>Ready</var>, <var>Failed</var>, or <var>Expired</var> proposal, such as editing, no longer work for it. Manage the generated IO and campaigns with the [Campaign API](/guidelines/campaign-api).

import {
  getInstance
} from "prerequisites"

const axios = getInstance();

interface Responses {
  200: {
    content: {
      "application/json": {
        success: boolean;
        data: {
          downloadUrl: string;
        };
      };
    };
  };
  422: {
    content: {
      "application/json": {
        success: boolean;
        errorObjects: {
          error: string;
        }[];
      };
    };
  };
}

function downloadPlan(): Promise<Responses> {
  const options = {
    method: 'POST',
    url: 'https://api.iqm.com/api/v3/plan/hcp/plan/download',
    requestBody: {
      content: {
        "application/json": {
          planId: `number`,
          fileTypeId: `number`,
        }
      }
    }
  };

  return axios.request(options).then(({ data }: { data: Responses }) => data);
}
