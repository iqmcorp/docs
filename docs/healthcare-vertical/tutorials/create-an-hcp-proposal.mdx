## About HCP plans

An HCP plan targets healthcare professionals by their National Provider Identifier (NPI) type, specialty, location, and data partner. Unlike Political plans, which go through separate strategy and proposal stages, an HCP plan is created directly with its targeting and proposed campaigns. Endpoints and fields that refer to a proposal, such as `/hcp/proposal/add`, work with the same HCP plan, and the plan's ID is used wherever a <var>planId</var> is required.

**Generate campaigns → Save plan → Edit (optional) → Publish IO and campaigns**

There are two key rules to keep in mind when working with HCP plans:
  1. **Targeting consistency:** The split strategy must agree with the plan-level targeting when you save, edit, or publish the plan. See [Step 1](#step-1-plan-the-audience-and-targeting).
  2. **Status echo:** Every edit and publish request must include the plan's *current* <var>statusId</var>. See [Step 5](#step-5-edit-the-plan).

## Before you begin

To create and publish an HCP plan, the following are required:

  * An account on the IQM platform in a Healthcare Workspace
    * See the [Getting started](/getting-started/before-you-begin) section to create an account and request a Client ID and Client Secret.
    * Planner API requests from a Workspace outside the Healthcare vertical are rejected.
  * An Advertiser Organization
    * Publishing and downloading a plan is only available to Advertiser Organizations.

All Planner times are Unix epoch **milliseconds**, not seconds. For example, November 1, 2026 at 00:00 US/Eastern is <var>1793505600000</var>.

### Step 1: Plan the audience and targeting

Before calling any endpoint, decide who the plan targets and how its campaigns are split. These choices make up the body of every request in the following steps. See [HCP Planner resource properties](/healthcare-vertical/planner#hcp-planner-resource-properties) for all fields.

#### NPI types

<var>npiTypeIds</var> sets which professionals to reach. Get values from the [NPI type list](/healthcare-vertical/planner#npi-type-list).

<EnumWidget values={npiTypes} />

#### Audience blocks

<var>audienceBlocks</var> defines the audience. Each block uses one audience selection method, set by <var>audienceSelectionMethodId</var>, and the fields a block needs depend on its method. Use at most one block per method. See [Get audience selection methods list](/healthcare-vertical/planner#get-audience-selection-methods-list).

| Method | ID | Required block fields | Audience type |
| --- | --- | --- | --- |
| Filter based | <var>1</var> | <var>speciality</var>, <var>locations</var>, <var>dataPartners</var> | Matched audience (<var>1</var>) |
| Upload NPI list | <var>2</var> | <var>speciality</var>, <var>locations</var>, <var>dataPartners</var>, and <var>storagePathId</var> from an uploaded NPI file | Matched audience (<var>1</var>) |
| Existing audience | <var>3</var> | <var>includeAudienceIds</var> and/or <var>excludeAudienceIds</var>, up to 14 in total. Don't send specialty, location, or data partner fields. | Taken from the selected audiences |
| Account based | <var>4</var> | <var>speciality</var>, <var>locations</var>, <var>account</var>, <var>accountType</var>, <var>healthSystem</var>, <var>title</var>, <var>dataPartners</var>. Requires NPI type <var>3</var>. | Account Based Marketing (ABM) audience (<var>9</var>) |

For filter-based blocks:
  * <var>locations.countryId</var> must be <var>30100001</var> (United States).
  * <var>dataPartners</var> is a list of partners with at least one marked <var>selected: true</var>. See [Get data partners list](/healthcare-vertical/planner#get-data-partners-list); the active partners are <var>7</var>, <var>8</var>, <var>11</var>, and <var>12</var>.
  * <var>speciality</var> uses the "select all" pattern described below. See [Get specialties list](/healthcare-vertical/planner#get-specialties-list).

The audience type of each block is set by IQM from its method, as in the table above. Don't send <var>selectedAudienceTypeIds</var>; it is ignored.

#### Plan-level targeting

<var>planLevelTargeting</var> sets the creative types, devices, channels, and inventory for the whole plan. All four objects are required: a request without <var>channels</var> or <var>inventory</var> returns a generic <var>500</var> error. To target all channels and all Open Exchange inventory, send:

```json title="Channels and inventory, all selected"
"channels": {
  "channelTypeIds": [],
  "allChannelTypesSelected": true
},
"inventory": {
  "openExchanges": {
    "exchangeIds": [],
    "allExchangesSelected": true,
    "iabCategoryIds": [],
    "allIabCategoriesSelected": true
  }
}
```

Objects such as <var>creativeTypes</var>, <var>devices</var>, <var>channels</var>, and <var>speciality</var> use a "select all" flag with an ID list:

  * Select all: set the flag (for example <var>allCreativeTypesSelected</var>) to <var>true</var> and send an empty ID list.
  * Select specific values: set the flag to <var>false</var> and list the IDs.

Any other combination is rejected.

#### Split strategy and the targeting consistency rule

<var>splitStrategy</var> decides how the plan is divided into campaigns. Each entry names a [split dimension](/healthcare-vertical/planner#get-split-strategy-list) and the values to split by. Each listed value becomes its own campaign slice, and campaigns are created for every combination of slices. A split strategy must include the creative type dimension, and the NPI type dimension unless the only audience block is an existing audience.

The values in each split dimension must agree with the plan's targeting when you save, edit, or publish the plan (Steps 3, 5, and 6). This is the most common cause of rejected HCP requests. Generating campaigns (Step 2) doesn't check the rule: it ignores <var>selectedValueIds</var> and splits by every plan-level value of each listed dimension. For example, an NPI type split of <var>[3]</var> on a plan targeting NPI types <var>3</var> and <var>4</var> still creates campaigns for both. See [Targeting consistency rule](/healthcare-vertical/planner#targeting-consistency-rule).

| Split dimension | <var>splitDimensionTypeId</var> | <var>selectedValueIds</var> must agree with | Rule | Campaign field |
| --- | --- | --- | --- | --- |
| Creative type | <var>1</var> | <var>planLevelTargeting.creativeTypes.creativeTypeIds</var> | Exact match | <var>targeting.creativeTypeId</var> |
| NPI type | <var>2</var> | <var>npiTypeIds</var> | Subset | <var>targeting.npiTypeId</var> |
| Data partner | <var>3</var> | <var>dataPartners[].id</var> across all audience blocks | Subset | <var>targeting.dataPartnerIds</var> |
| Device type | <var>4</var> | <var>planLevelTargeting.devices.deviceTypeIds</var> | Subset | <var>targeting.deviceTypeIds</var> |
| Audience type | <var>5</var> | Audience types of all audience blocks | Subset | <var>targeting.audienceTypeIds</var> |

When "select all" is used for creative types or devices, compare against the full list: creative types <var>11</var>, <var>13</var>, <var>14</var>, <var>15</var>, and <var>17</var>; devices <var>20300001</var> to <var>20300004</var>.

:::caution

Mismatches are reported with a general message, such as <var>Selected creative type IDs and split IDs do not match.</var> Check the dimension named in the message against the table above.

:::

Each proposed campaign's targeting uses singular fields for creative and NPI type (<var>creativeTypeId</var>, <var>npiTypeId</var>), unlike the plural fields at the plan level. Campaign targeting isn't checked against the split strategy, so let IQM build the campaigns in [Step 2](#step-2-generate-campaigns) rather than writing them yourself.

### Step 2: Generate campaigns

<CopyUrl method="POST" url="https://api.iqm.com/api/v3/plan/hcp/generate-campaigns" operationId="generateHCPProposedCampaigns" />

<div class="endpoint-container">
  <div class="child1">

Send the plan details from Step 1 without campaigns. IQM builds the proposed campaigns from the split strategy, forecasts their reach, and calculates each campaign's CPM, impressions, and budget range, along with the plan's totals. Nothing is saved.

Use the response as the request body for Step 3. You can change budgets and impressions within each campaign's minimum and maximum before saving.

Each campaign's <var>dataCpm</var> is the average data cost of its selected data partners, and its <var>mediaCpm</var> depends on its creative type. For example, video campaigns have a higher media CPM than image campaigns.

### Step 6: Publish the IO and campaigns

<CopyUrl method="POST" url="https://api.iqm.com/api/v3/plan/hcp/campaigns/publish" operationId="generateIOCampaigns_2" />

<div class="endpoint-container">
  <div class="child1">

Publish the plan to create an IO and campaigns. Send the full plan with its <var>id</var> and current <var>statusId</var>, as in Step 5. Publishing saves the request body first using the same checks as an edit, so the [status echo rule](#step-5-edit-the-plan) applies here too.

The request returns immediately and the plan moves to <var>Processing</var> (<var>5</var>) while the audiences, IO, and campaigns are created in the background. When publishing finishes, the plan moves to <var>IO Created</var> (<var>7</var>) and its <var>ioId</var> is set. If publishing fails, the plan moves to <var>Failed</var> (<var>4</var>) and you can publish it again. The response doesn't include the IO ID: use [Step 4](#step-4-get-plan-details) to check the result. Publishing can take more than a minute. It has finished successfully when <var>statusId</var> is <var>7</var>, <var>ioId</var> is greater than <var>0</var>, and every campaign's <var>campaignId</var> is greater than <var>0</var>.

The campaigns are created as drafts. They don't run until creatives are attached and the campaigns are approved.

The request schema is the same as [Step 5](#step-5-edit-the-plan), except for the fields in the table below.

:::danger

Publishing is a one-way step. A published plan can't be returned to <var>Ready</var>, and calls that require a <var>Ready</var>, <var>Failed</var>, or <var>Expired</var> plan, such as editing, no longer work for it. Manage the generated IO and campaigns with the [Campaign API](/guidelines/campaign-api).

:::
